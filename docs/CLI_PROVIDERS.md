# Local CLI support

Checked 2026-09-11. Recalloom is free software with optional donations. Users connect their own supported AI access; Recalloom does not sell inference or operate a shared account. Local document processing does not make the provider's model inference local.

Image-suggestion update, 2026-09-13: the installed Codex CLI 0.154.0-alpha.6.2 reports `exec --image <FILE>...` in its help. Recalloom stages one validated source PNG in the temporary request directory and attaches it while retaining its existing read-only/no-shell/no-web configuration, ephemeral mode, stdin prompt, and JSON schema. No arbitrary image path comes from the model. The [Codex CLI reference](https://developers.openai.com/codex/cli/reference) documents the non-interactive command; installed help and the synthetic live check establish the image flag behavior for this version. One Low-reasoning request returned three correctly placed rectangles over a synthetic diagram's labels. Claude/Gemini/Kimi image routes are not implemented and explicitly reject this task; there is no cross-provider fallback. Suggestions are temporary and require a separate user action to become notes.

The protocols come from the [Codex app-server reference](https://developers.openai.com/codex/app-server/), [Claude CLI reference](https://code.claude.com/docs/en/cli-reference), Anthropic's [official SDK initialization implementation](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/_internal/query.py), [Gemini ACP guide](https://geminicli.com/docs/cli/acp-mode/), and [Kimi ACP reference](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-acp.html). There is no new Python SDK dependency: the app invokes native executables or official npm entry points through Node, using argument arrays and the CLIs' supported authentication stores.

Provider, model, and reasoning are dropdowns. Card formats remain checkboxes; learning focus remains a single visible choice. Model/effort combinations are validated before generation, and provider/model/effort are retained on retry and in version-7 backups. Changing providers clears consent to share the lecture text. No failure silently switches providers.

Models are discovered instead of maintained as a hardcoded list. In this installation, Codex reported Astra/Sol/Terra/Luna plus GPT-5.5; Claude reported its default, Opus, Fable, Sonnet variants, and Haiku aliases. Their reasoning capabilities differed: some included Extra high and Max, while Haiku reported no effort control. These are observations from the installed CLI, not a guarantee of account entitlement, model quality, or the latest provider catalog. Refresh after CLI/account changes. Recognized effort values are default, none, minimal, low, medium, high, xhigh, and max, plus Kimi's model-specific off/on controls. Gemini stays at CLI default because the checked ACP interface exposes no separate effort setting. Agent-orchestration modes are excluded.

Only sanitized model IDs, labels, effort capabilities, and a refresh timestamp are cached under ignored `data/models-*.json`. Metadata exchanges have bounded time/output and reject host action requests. Refreshing submits no inference prompt; CLIs may contact their provider for metadata or authentication. Passwords, tokens, raw authentication responses, and account details are not cached or included in backups.

Claude generation uses safe mode with custom settings, hooks, memory, normal tools, and MCP integrations disabled. It retains supported subscription login; `--bare` would bypass that login, as explained in [Claude's headless guide](https://code.claude.com/docs/en/headless). Detected custom endpoints/API credentials and Bedrock/Vertex/Foundry profiles are rejected by this integration. It does not change those profiles. Source text goes through stdin; result envelopes and source references are validated separately. Account restrictions and managed CLI policies still apply.

## Gemini and Kimi implementation details

Both use separate CLI-owned profiles under `~/.recalloom/cli/`, so users sign in once from Recalloom even when they already use these CLIs for coding. No existing token files are read or copied. The app creates restricted configuration, disables normal tools/hooks, passes empty MCP servers, and denies ACP host file/terminal/permission requests. Changed profile restrictions cause a visible error instead of being silently overwritten. Inherited API-key/custom-endpoint and Node injection variables are removed from the subprocess environment. These are CLI restrictions, not a general OS sandbox. The settings were checked against the installed official npm packages, not just a generic ACP specification.

Gemini's profile uses `GEMINI_CLI_HOME`, with configuration under its `.gemini/settings.json`. Its fresh configuration deliberately omits `selectedType`: the installed version can otherwise start OAuth before ACP initialization, even with external authentication enabled. An isolated diagnostic encountered that behavior; no account sign-in completed and no model was called. The corrected fresh-profile startup passes. Only explicit Connect starts the browser authentication handshake. GET connection status reads an app-created completion marker, not credentials; it cannot prove token validity. Non-login processes suppress browser launching. **Sign in again** provides explicit recovery for expired accounts. See [Google authentication](https://geminicli.com/docs/get-started/authentication/).

Kimi's current supported package is the **TypeScript/Node CLI `@moonshot-ai/kimi-code`**, not the earlier Python CLI or a Rust CLI. `KIMI_CODE_HOME` isolates its settings, credentials, and history. Its ACP `authenticate` validates saved login without launching the browser; the separate `login` command owns device authorization. The account-website selector passes the validated global/mainland-cn region to that command, or leaves the saved/default region in control. Empty tool allowlists mean defaults in the checked implementation, so Recalloom uses a nonmatching tool allowlist plus a deny-all permission rule. Its managed model IDs use `kimi-code/`; custom providers are excluded. Discovery queries each model's thinking capabilities without sending a prompt. See [installation](https://www.kimi.com/code/docs/en/kimi-code-cli/getting-started.html), [environment configuration](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/env-vars.html), and [provider configuration](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/providers.html).

Generation uses a bounded JSON-RPC transport with cancellable stdin writes, output limits, session identity checks, and a per-batch deadline. Truncated/non-JSON output and tool requests fail without importing that batch; previous batches and accepted edits survive. Gemini uses `session/set_model`; Kimi uses `session/set_config_option` for model/thinking. The normal draft/source validators still apply after JSON parsing. There is no fallback to another provider. These CLIs can retain their own session history under the dedicated profile; converter backups exclude it and deleting a lecture does not erase that history.

The offline suite and browser checks exercise synthetic model lists, per-model controls, malformed/truncated/foreign-session output, permission/file/tool requests, blocked stdin, timeout/cancellation, connection deduplication, CSRF restrictions, retry preserving edits/settings, and version-7 backup restoration with Kimi thinking toggles. Real account authentication and inference remain the next validation step; protocol initialization alone does not establish generation compatibility or quality.

## Other commonly used options researched

These integrations are **not implemented**. Findings concern authentication and integration feasibility, not a generation-quality or cost comparison.

| CLI / provider | Official route found | Fit for a later addition |
| --- | --- | --- |
| Cursor | Official `agent login` browser sign-in, `agent status`, model discovery, and `agent acp` for custom clients; current installation docs include native Windows | Feasible using each user's own Cursor account and allowance. Its adapter still needs authenticated model/effort mapping, native startup checks, restricted tools/hooks/MCP, bounded generation, and recovery tests. Not implemented or installed here. [Authentication](https://cursor.com/docs/cli/reference/authentication), [parameters](https://cursor.com/docs/cli/reference/parameters), [ACP](https://cursor.com/docs/cli/acp), [installation](https://cursor.com/docs/cli/installation) |
| DeepSeek | The official Claude Code integration uses a DeepSeek API key and a custom endpoint | This is a separately billed API integration, not evidence that a DeepSeek chat subscription supplies the requested CLI sign-in. Recalloom's Claude subscription adapter intentionally does not enable this route. [Official integration guide](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/) |
| Qwen Code | Current documentation says Qwen OAuth has been discontinued; it lists coding-plan/token-plan and API-key routes | Do not advertise the former free OAuth login as a working connection option. Reassess if adding explicit API access later. [Current authentication documentation](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/) |

Cursor is a plausible next addition because its official ACP mode supports custom local clients. Its default agent mode has full tool access, and even read-only modes need restriction review for lecture generation; simply invoking print/ask mode would not establish isolation. Finish real-account validation of the requested adapters before expanding the provider list further. Authentication feasibility does not establish exact plan entitlement, remaining allowance, or blanket permission for a shared hosted service.
